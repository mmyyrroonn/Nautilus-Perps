## Findings

### N1 — P1: A definitively rejected close permanently consumes its full reservation

Initial `production.rs:509-517` computed consumed close capacity from an evidence order when present/settled, otherwise its full reservation. `execution.rs` definitive-refusal branches call `guard.definite_zero(id)` and then `reporter.forget(id)` (initial lines 5055-5092; current calls around 5065/5082/5099). A first reduce-only close refused by the venue therefore disappears from `evidence.orders` and is counted as fully reserved, despite authoritative zero execution. The second permitted reduce-only attempt is rejected as exceeding confirmed residual, leaving the filled entry exposed.

The existing terminal-partial-close test keeps the terminal order row and does not cover this branch. The unknown-result branch must continue to reserve the full uncertain quantity.

Current status: a `known_zero` skip was added to the capacity loop during review (`production.rs:512`). Source correction is present; verified resolution is pending. Required regression: actual native filled entry -> first close definite zero/refusal -> second close allowed for exact residual, with mock wire count/quantities; companion unknown-close case must retain reservation and refuse a conflicting second close.

### N2 — P1: Genuine DMS expiry was not rechecked after durable persistence

Initial `production.rs:543-549` rechecked entry/cleanup deadline, quote age and `evidence.ready` after main-journal checkpoint and sidecar `sync_all`, but omitted the authority's genuine `dms_confirmed_deadline`. The earlier check at about 474 used the time before potentially slow persistence. The legacy machine's DMS timer can remain Armed beyond the genuine send-based deadline: the existing short-DMS regression explicitly demonstrates this distinction. A checkpoint crossing the genuine deadline could therefore still authorize a POST with `evidence.ready=true`.

Current status: a `send_now >= dms_confirmed_deadline` refusal was added during review (`production.rs:547`). Source correction is present; verified resolution is pending. Add a deterministic checkpoint-boundary regression using the internal evidence-reader seam or equivalent existing fixture support: persistence begins while genuine protection is valid and finishes after it expires; zero POST bytes may leave. Keep the full command/wire tests in addition to a predicate test. Do not add production test-only bypasses.

### N3 — P1: Socket write is still promoted to confirmed DMS release / final clean

`execution.rs` ordered stop release branch (current around 2436-2448) calls `stream.send_switch_frame`, and on `Ok(())` immediately calls local `.release(...)` and sets `report.released_switch=true`. It does not wait for an authenticated venue `unsubscribed` acknowledgement. `session.rs:600-617` already parses that event; the stream's `PrivateEvent::Unsubscribed` branch (current 757-762) records diagnostics only. `guard.finish(complete)` then upgrades a retained reconciled snapshot to `phase=final, shutdown_status=clean`.

Thus a successful socket enqueue followed by a dropped, refused or never-acknowledged release can still claim clean shutdown. This is the same evidence distinction correctly implemented for DMS arm: sent is not acknowledged. The parent independently identified this issue and it was confirmed from the actual call chain.

Required correction: retain a pending production release associated with this stream/run, and only establish confirmed release from a genuine matching outstanding unsubscribe acknowledgement. Bound the wait by the remaining shutdown/cleanup allowance. Missing, wrong-channel, stale, unsolicited, refused or timeout acknowledgement must remain unknown/dirty, not clean. Natural timeout must not be guessed as a confirmed unsubscribe. Tests must complete an actual native IOC cycle with missing/delayed/wrong release ACKs and inspect final snapshot/verdict; current mock always acknowledges unsubscribe and only tests sent frames. Preserve readonly zero-DMS behavior.

### N4 — P1: The in-progress stronger release guard requires protection state that stop clears

During review, `validate_direct_switch` was strengthened to require unexpired `state.dms_confirmed_deadline` and a current authoritative reconciled proof (`production.rs`, current around 761-775). However both `disconnect` and synchronous `stop` call `account.note_session_ended`, which calls `guard.invalidate`; `invalidate` unconditionally clears that deadline (`production.rs:336-341`). This happens before the ordered release reaches `validate_direct_switch`.

The strengthened guard therefore appears to reject every otherwise clean production release through the mandatory stop sequence. This is a source-ordering finding in the newly edited code, not a rerun result.

Required correction: separate admission invalidation from retained stop/protection evidence, and let the private ordered-release path use precisely the evidence it can still justify. Do not merely delete the deadline/proof checks or reopen direct arm/renew writes. Re-run the real native IOC complete lifecycle and dirty-stop paths after N3/N4 are resolved together. A release must be both permitted by ordered-stop ownership and acknowledged by the host.

### N5 — P2: Native minimum-notional currency policy still treats USD and USDC as interchangeable

`execution.rs` production `submit_order` minimum check (current around 4981-4998) accepts either USD or USDC, then drops the currency and passes a scalar amount to the authority. Ondo native instruments are quoted in USD, settled in USDC. The parent/app ruling explicitly requires minimum currency equal to applicable quote currency, with no implicit conversion/parity. A direct native command can therefore compare a USDC minimum numerically with USD quantity times limit price, while the reviewed app correctly refuses that combination.

Required correction: compare the actual Money minimum currency with the actual approved instrument quote currency before discarding it. An absent standalone minimum stays None/unpublished; do not replace it by zero or the user's USD10 target. Extend `test_production_real_money_minimum_is_enforced` with USDC-on-USD rejection as well as matching USD and mismatching EUR. Existing USD/EUR cases do not cover this mismatch. Update the native interface text that currently says USD/USDC both qualify.

The app also consumes `available_margin_usd` and compares it with USD entry notional plus a USD buffer (`ondo_trade_probe.py:1537-1545,2857-2859`). Parent ruling for the bounded current probe: require an exact `min_available_margin_usdc="25"` operator safety threshold in the hash-bound app plan/limits and native envelope constructor, report `available_margin_usdc`, and compare USDC only with that same-unit USDC threshold. The USDC threshold is neither a venue minimum nor proof of an FX/parity conversion or guaranteed sufficient margin; the venue remains the final margin arbiter. Missing/malformed/wrong-unit margin stays unavailable/refused.

Native and app owners are updating the contract. The prior app scope verdict did not cover this newly discovered schema/unit issue. Before acceptance, update every constructor/schema/report/readiness path and exact-signature test, refuse the obsolete USD key rather than silently alias it, test below/equal/above the USDC threshold, and prove no remaining USDC-vs-USD arithmetic in the guards. This additional contract change requires a coordinated frozen native/app rereview and focused/full regression evidence. Source edits are in progress and are not yet verified here.
