## 正文

### 一、具体策略写在回调里吗？

可以这样理解：**回调是框架进入你的策略代码的入口，业务逻辑可以由回调调用其他函数完成。**

例如 rc4 的 Strategy 暴露了这些入口：

| 回调 | 触发场景 | 你通常放什么逻辑 |
|---|---|---|
| `on_start()` | 策略启动 | 订阅 A、B 行情，初始化定时器 |
| `on_quote(quote)` | 收到订阅的买一卖一报价 | 更新该市场的报价视图，重新评估 |
| `on_book_deltas(deltas)` | 收到订阅的盘口增量 | 使用最新订单簿重新估算可成交价格 |
| `on_time_event(event)` | 定时器触发 | 检查行情超时、订单超时、定期记录 |
| `on_order_filled(event)` | 收到成交事件 | 更新双腿已成交数量和未对冲敞口 |
| `on_order_rejected(event)` | 收到订单拒绝 | 进入失败处理或恢复流程 |

这些名称见本地 [Strategy 接口](E:/Nautilus-Perps/.venv/Lib/site-packages/nautilus_trader/trading/__init__.pyi:601)。只覆盖自己需要的回调即可。

一个容易维护的分工是：

1. 回调接收事件、更新状态。
2. 行情检查函数判断两侧是否可用、是否新鲜。
3. 定价函数按目标数量计算两侧扫盘均价和成本。
4. 决策函数判断是否满足开仓、平仓条件。
5. 执行协调逻辑跟踪双腿订单及失败恢复。

这些辅助函数、类和文件如何组织，由项目决定。NautilusTrader 没有规定你的价差函数必须叫某个名字。简单策略可以写在一个类里，复杂后再拆分。

回调中应避免同步 HTTP 查询、长时间计算或睡眠：处理耗时会影响后续事件的处理速度。重型计算需要单独设计任务调度、结果回传及状态一致性。

另一个关键点：跨所策略还包括“下单后怎么办”。只写 `价差超过阈值 → 下单`，尚未涵盖部分成交、另一腿拒绝、重复触发和重启恢复。

### 二、A 报价触发回调，然后读取 B 吗？

对，通常读取 **B 最近已经进入本地系统的行情**。正常行情路径中，A、B 的订阅一直各自接收推送。

用事件先后顺序看最清楚：

| 本地处理顺序 | 收到的事件 | 可用于评估的组合 |
|---|---|---|
| 第 1 条 | B 的报价 B1 | A 尚无数据，暂不评估 |
| 第 2 条 | A 的报价 A1 | A1 与 B1 |
| 第 3 条 | A 的报价 A2 | A2 与 B1 |
| 第 4 条 | B 的报价 B2 | A2 与 B2 |

所以 A 更新可以触发计算，B 更新也可以触发计算。你可以在策略里保留 `latest` 字典，或者通过框架 Cache 读取。rc4 对应接口是 `self.cache.quote(instrument_id)`，深度簿是 `self.cache.order_book(instrument_id)`，见 [Cache](E:/Nautilus-Perps/.venv/Lib/site-packages/nautilus_trader/common/__init__.pyi:284)。

下面只展示回调与本地状态之间的关系。`a_id`、`b_id` 和 `latest` 假定已在策略构造时初始化；辅助函数由项目自行实现。它不是可直接运行的完整程序，也没有下单代码。

```python
def on_start(self):
    self.subscribe_quotes(self.a_id)
    self.subscribe_quotes(self.b_id)

def on_quote(self, quote):
    if quote.instrument_id not in (self.a_id, self.b_id):
        return

    self.latest[quote.instrument_id] = quote
    a = self.latest.get(self.a_id)
    b = self.latest.get(self.b_id)
    if a is None or b is None:
        return

    if not self.market_data_is_usable(a, b):
        return

    self.evaluate_pair(a, b)
```

**“两个都有值”和“可以用来交易”是两件需要分别检查的事。**

- B 可能已经几秒钟没有更新，虽然它仍留在缓存里。
- A1 与 B1 通常不来自同一时刻，不能视为全球同步快照。
- 网络重连后，深度快照与增量可能还没有重新衔接完成。
- 一组订单如果仍在处理中，新行情不能随意触发重复建仓。

因此，应根据策略容忍度检查两侧更新年龄、时间差、连接及簿同步状态，并设置双腿订单状态门槛。时间戳的来源与时钟偏差也要区分；在回调里记一次当前时间，只能说明这次回调的处理时间，不能自动排除消息此前在队列中积压。

数据不足时，通常跳过这次评估，等待后续推送。初始化或断线恢复时可能使用 HTTP 快照，那属于数据维护流程。

```python
subscribe_book_deltas(
    instrument_id,
    book_type,

```

见 [深度订阅签名](E:/Nautilus-Perps/.venv/Lib/site-packages/nautilus_trader/trading/__init__.pyi:689)。使用受支持的深度订阅并设置 `managed=True`，可要求数据引擎管理订单簿；保留默认值时，可以自行构造 OrderBook 并应用增量。采用哪一种方式，应明确且保持一致，避免把同一增量应用两遍。

### 三、费用与深度在哪里考虑？

**交易前是否值得做，由你的策略成本模型判断；框架提供行情、订单簿、订单、账户和模拟模型等基础能力。**

可以按职责拆成五层：

| 层次 | 负责什么 | 费用与深度如何出现 |
|---|---|---|
| 适配器与数据处理 | 接收、解析、标准化交易所信息 | 提供盘口和合约定义；实际账户费率的来源需逐所核实 |
| 策略的定价／成本函数 | 交易前评估 | 目标数量、扫盘均价、maker/taker 费率、成本预留、开平仓条件 |
| 风险约束 | 限制风险 | 通用限额加策略专属的最大未对冲敞口、行情超时和双腿状态限制 |
| 执行及账户记录 | 跟踪真实结果 | 成交数量、实际价格、commission、仓位；手续费与资金费分别对账 |
| 回测／模拟 | 构造模拟结果 | FeeModel、FillModel 等决定模拟费用和成交行为 |

rc4 的 [RiskEngineConfig](E:/Nautilus-Perps/.venv/Lib/site-packages/nautilus_trader/risk/__init__.pyi:50) 有订单提交频率、改单频率、单笔名义金额等配置。你定义的“净价差至少多少”“未对冲最多多久”仍需项目代码实现，不能从这些通用配置推定已经覆盖。

#### 用具体数量计算深度

假设买 A、卖 B，数量都为 5 个基础单位，均为相同计价币种的线性产品，合约乘数为 1。以下数字完全是假设：

- A 卖盘：100 元有 2 个，101 元有 3 个。
- B 买盘：100.8 元至少有 5 个。

A 买入 5 个的盘口加权均价为 `(100×2 + 101×3) / 5 = 100.6`。B 卖出均价为 100.8。

所以当前盘口隐含的建仓价差价值是 `5 × (100.8 - 100.6) = 1` 元。只比较买一卖一会得到 `5 × (100.8 - 100) = 4` 元，高估了可执行的价差。

如果假设双方开仓 taker 费率都是 0.04%，两边开仓费合计为 `503×0.0004 + 504×0.0004 = 0.4028` 元。扣除这两笔开仓费后的价差价值为 `0.5972` 元，尚未计入平仓、资金费和行情变化。

rc4 的 [OrderBook 定价接口](E:/Nautilus-Perps/.venv/Lib/site-packages/nautilus_trader/model/__init__.pyi:3961) 包括 `get_avg_px_for_quantity()`、`get_worst_px_for_quantity()`、`simulate_fills()`。它们可辅助计算；**仍须验证目标数量是否能被当前有效深度完整覆盖**，不能把“返回了一个均价”当作“足量且保证成交”。具体边界行为进一步阅读实现或写离线测试。

#### 成本计算的几个边界

1. 买入消耗 asks，卖出消耗 bids。数量要先统一到经济敞口，不能仅比较两个交易所都写着“1 张”。
2. 使用扫盘均价时已经计入了当前可见价差和跨档成本；另加成本预留时说明覆盖的是延迟、盘口撤单等额外风险，避免重复扣同一项。
3. maker 费率以实际成交角色为准。一个普通限价单如果立即吃掉对手盘，也可能是 taker。
4. 账户费率档位、返佣、市场优惠可能变化。Instrument 的默认费率不必然等于你的实际账户费率。
5. 当前展示深度只能用于估算，订单到达时盘口可能已经变化。

#### 开仓价差价值与整轮收益

对前述同币种、乘数为 1、数量相同的线性双腿仓位，忽略中途数量变化：

```text
整轮毛交易盈亏
= q × [(B 开仓卖价 - A 开仓买价) - (B 平仓买价 - A 平仓卖价)]

整轮净盈亏
= 整轮毛交易盈亏
- A 开、B 开、A 平、B 平四笔手续费
+ 持仓期间实际净资金费
- 其他实际成本
```

开仓时的价差不是即时兑现的净利润。平仓价差、持仓时间和实际执行共同决定最后结果。跨币种、反向合约或不同乘数产品须换成相应的估值公式。

模拟费用入口见 [FeeModel](E:/Nautilus-Perps/.venv/Lib/site-packages/nautilus_trader/execution/__init__.pyi:134)，真实成交信息见 [OrderFilled](E:/Nautilus-Perps/.venv/Lib/site-packages/nautilus_trader/model/__init__.pyi:4366)。配置一个回测 FeeModel，并不代表实盘开仓判断已经自动扣除了费用。

### 四、L2 常见，L3 很少吗？

就你关注的加密永续公开行情接口而言，**L2 是常见起点，L3 的可获得性更有限**。这是一项工程上的概括，本篇没有对所有交易所做数量统计。

关键区别：

- L2：每个价格档位的聚合数量。例如“100 元总共有 12 个”。
- L3：逐笔可见挂单。例如同一价格有订单 X 的 5 个、订单 Y 的 7 个，后续按订单 ID 更新。
- 档位数量和订单粒度是两个维度。L2 可以有很多档，L3 也可以只订阅有限深度。

当前公开资料中的具体例子：

- Binance USDⓈ-M 的 depth 通道提供买卖盘更新，见 [官方深度流文档](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/ws-streams/public#diff-book-depth-streams)。
- Hyperliquid 的 `l2Book` 为价格层级数据，`n` 是该层订单数，并未列出每一笔订单，见 [官方订阅文档](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/websocket/subscriptions)。
- Lighter 的 `order_book` 返回 asks/bids 内的 `price`、`size`，见 [官方 WebSocket 文档](https://apidocs.lighter.xyz/docs/websocket-reference)。
- L3 也有公开说明的实例：Kraken Spot 的 `level3` 提供逐笔可见挂单，订阅要求认证 token；冰山单隐藏数量等不在数据中，见 [Kraken 官方说明](https://docs.kraken.com/exchange/api-reference/spot-websocket-v2/level3)。

私有账户通道带有自己的订单 ID，只说明可以跟踪自己的订单，不足以证明市场行情为 L3。

对于双边 taker 成本估计，可靠的 L2 已能支撑当前展示深度的扫盘计算。对于 maker 排队分析，L3 更有帮助，但隐藏流动性、延迟和撮合规则仍影响结果。框架支持 `L3_MBO` 也不能让一个只收到 L2 数据的适配器凭空生成真实逐笔挂单。

## 小结

1. 回调提供入口，辅助函数承担业务计算，订单事件完善策略闭环。
2. A、B 行情各自推送；一侧更新时通常使用另一侧已有的本地最新值，两侧时间可能不同。
3. 深度、费用和风险分属多个职责层；净收益判断必须在策略中明确实现。
4. L2 按价格聚合，L3 按可见订单区分；深度档数与数据粒度分别考虑。
5. 本地已核验 rc4；先读 `.pyi` 掌握接口，内部实现再对齐同一上游标签。

可以用三个问题自测：B 五秒没更新，但 A 频繁更新时怎么办？A 第一档只有 2 个，计划买 5 个应怎样计价？订单已提交但尚无回报，新行情到来能否再开一组？答案依赖你定义的状态与风险规则，不能仅凭价差作决定。
