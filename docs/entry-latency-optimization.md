# 入场链路延迟优化与验收

按补齐测量、减少重复计算、缩短调度等待、处理剩余队列瓶颈的顺序推进。
基线说明见 [2026-10-19 实测记录](../reports/opportunity-trading/vultr-eu-entry-pricing-20261019.md)：
单次 `strategy.entry` 平均约 40 微秒；76～100 ms 是到 Python 回调的行情交付年龄。
盘口发布与机会评估另有 100 ms 周期，三者不能当成同一阶段的耗时。

## 第一轮：Python 候选实现

- 给现有有界计时报告补 p99，采样记录行情交付年龄、首次/末次盘口更新到发布、发布到评估。
- 对实际成立且通过后续核验的候选记录持久化、执行协调器等待与 Python 提交边界，分别观察提交后的不同结果。
- 同一不可变快照只校验一次档位、排序、价格/数量及覆盖范围；同一不可变元数据只校验一次数量规则与费用来源。
  对象替换天然换版，缓存不按价格或时间戳命中；数量、深度、费用、步长和最小名义额变化不会复用旧对象结果。
- 把保守的最佳报价上界移到配对准备前。保留精确 Fraction 定价、纸面流动性扣减、
  新鲜度、时间偏差、连接/交易有效状态、账户与订单归属核验、持久化及发送前门禁。

本轮不调整评估周期、组合调度或 native 队列。Python 可观测边界及统计限制见
[诊断说明](memory-diagnostics.md#pipeline-latency-boundaries)。
精确的 native 入队时刻与网络写出时刻尚未暴露，不能用交付年龄和 `submit_order` 冒充。

| 4 | 新意图唤醒协调器 | 确认候选到提交的等待显著后实施；唤醒必须发生在持久化成功后，并保留发送前风控和订单幂等。 |

## 每轮验收

1. 保存候选前源码及哈希，保留现有用户改动；使用同一回放输入检查候选、数量、价格、费用、
   订单意图和状态。覆盖无机会、精确阈值、深度不足、同价不同量、元数据换版、
   过期/未来时戳、断连/停牌、纸面扣减、账户与待处理订单变化。
2. 分开报告无利润组合和可成交候选的耗时；计入新快照首次校验和创建成本，避免只测缓存命中。
   合成回放用于确定性回归，不等同于录制的真实行情回放。
3. 切换候选后，等待本次账户门禁与订阅健康条件满足，再取连续 **20～30 分钟新入场未暂停** 的窗口。
   观察 `phase`、`entry_pause_reason`、halt、盘口健康、CPU、各通道队列、RSS/swap、延迟行样本量及分位数。
   中途入场暂停必须另分窗口；查清原因后重新取得完整活跃窗口，不能放宽余额或时间边界来凑时长。
4. 对比相同配置、native 身份与采样机制，并记录行情速率和健康覆盖率。自然行情负载不同，
   不能把全部 CPU、队列或延迟变化归因于优化。当前分位数为最近有界样本，不是整个窗口分位数。
5. 订单候选不足时，将候选→提交、提交→接受/成交标记为样本不足；不要为收集样本制造额外交易。
