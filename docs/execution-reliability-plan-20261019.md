## 问题一：订单终态确认过早，保护状态缺少核对后的恢复路径

### 改动范围

- Python：`src/opportunity_native_execution.py` 的终态释放与恢复查询；`src/opportunity_live.py` 的成交归属、保护状态和核对完成条件。
- Native fork：Lighter 订单状态与成交流的衔接，主要涉及 `crates/adapters/lighter/src/websocket/parse.rs`、`websocket/handler.rs`、`execution.rs`。

### 实施步骤

1. 明确交易所订单终态、最终累计成交量、已处理成交明细之间的契约。缓存关闭且两边成交量相等不再单独充当“不会再有成交”的证明，尤其不能用暂时的 0=0 放行。
2. 先核实 Lighter 终态消息中的累计成交量是否具备最终性；如可用，保留并传递该证据，待成交明细累计量一致后释放应用终态。如不足，查询原订单与成交明细完成核对。不得丢弃晚到成交或用固定睡眠替代证明。
3. 为这类可核对的保护增加明确恢复条件：原订单最终成交与明细一致、账户持仓和挂单为活动后的完整权威快照、持久化账本一致、无未知提交或待核对经济数据。证据缺失或矛盾时继续暂停。
4. 将可恢复的订单核对状态与持久化失败、未知归属成交等硬保护区分。恢复应有独立事件，记录依据与时间；不能因为总仓位暂时为 0 就清除所有保护，也不能依赖重启清除。

- 逐笔成交只入账一次，不漏记风险敞口；缺少最终证据时不提前完成订单。
